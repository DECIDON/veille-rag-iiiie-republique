Axe 2 — L'interface web · leçon 9/10

Facettes déterministes, text-to-SQL soupçonné

À la fin de cette leçon, vous saurez expliquer pourquoi la question « combien de discours de Jaurès en 1904 ? » ne doit surtout pas passer par le LLM.

Une facette est une agrégation, pas une génération

Une facette est la colonne de compteurs que l'on affiche à gauche d'un moteur de recherche : « Sénat (4 212) · Chambre (9 017) », par date, par orateur… Elle est calculée par le moteur d'index, par exemple avec les aggs d'OpenSearch ou un GROUP BY SQL. Le résultat est déterministe : à index égal et à filtre égal, la réponse est la même à chaque clic, sans coût de calcul. Les interfaces de référence de l'AN et du Sénat fonctionnent exactement de cette façon, et c'est ce qu'une interface construite sur Searchkit (Apache-2.0, interface React pour OpenSearch) reproduirait.

Le text-to-SQL, et pourquoi la veille s'en méfie

Le text-to-SQL traduit une question en langage naturel en requête SQL (Vanna, WrenAI). La perspective est tentante pour les comptages, mais elle est statistiquement dangereuse : le benchmark officiel cité par la veille (arXiv 2601.08778) mesure jusqu'à 62,8 % d'erreur même pour les meilleurs systèmes sur les questions complexes. Pour un service destiné à des historiens, un comptage faux vraisemblable est pire qu'une absence de réponse. La veille en déduit une règle (SYNTHESE §4) : les facettes reposent sur des agrégations déterministes, et le LLM n'entre jamais dans le compteur.

Le text-to-SQL garde une place, en complément : il peut répondre à des questions ad hoc de comptage sur les tables de métadonnées, à condition que le SQL généré soit affiché (une pratique visible chez Vanna et Wren) pour que le chercheur audite la requête avant de croire le chiffre.

Où vivent les données des facettes ?

Elles vivent dans l'index unique de la leçon 0004, et jamais dans un second magasin de données parallèle qui dériverait. OpenSearch agrège et recherche ; pgvector joint les vecteurs aux tables de métadonnées (le choix des frameworks reposait déjà là-dessus, ainsi que sur le pattern « serveur MCP en lecture seule » d'EU Parliament Monitor, SYNTHESE §5 ; MCP, Model Context Protocol, est un protocole d'interface entre les outils et les modèles).

À retenir. Compter est une agrégation déterministe sur l'index ; le LLM ne compte pas. Le text-to-SQL n'intervient qu'en complément, pour les questions ad hoc, et il affiche alors le SQL qu'il a produit.

Vérifiez que c'est acquis

1. Comment l'interface doit-elle calculer « discours de Jaurès, 1904, par mois » ?

Une agrégation SQL (ou des `aggs`) sur les champs orateur et date donne un résultat rapide, rejouable et auditable. Faire appel à un LLM pour un fait que l'on peut compter constitue une régression, c'est-à-dire un retour en arrière par rapport à la règle.

2. Quelle précaution minimale pour exposer du text-to-SQL aux chercheurs ?

Afficher le SQL rend l'erreur vérifiable, or le taux d'erreur atteint 62,8 % sur les benchmarks. Les deux autres options n'ont pas d'effet démontré sur la justesse.

Source principale : votre veille, SYNTHESE §4 ; benchmark : arXiv 2601.08778.
