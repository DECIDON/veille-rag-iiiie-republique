Axe 1 — Les données · leçon 1/6

Post-OCR : normaliser sans trahir le texte

Gagné à la fin : expliquer pourquoi la première brique du pipeline n'est ni un framework RAG ni un modèle, mais un étage de normalisation qui produit un JSON canonique par intervention.

Le problème : l'OCR laisse des traces

Le corpus est déjà OCRisé (l'OCR est hors périmètre), mais un Journal officiel du XIXᵉ s.OCR-isé arrive sale : accents instables, apostrophes typographiques variées, césures par trait d'union en fin de ligne, artefacts de colonnes. Or tout ce qui est encodé différemment de ce que l'utilisateur tapera ne sera jamais retrouvé, ni par le moteur lexical, ni par l'embedding.

Le geste technique : Unicode NFKD + règles + dictionnaires

Un même « é » peut exister en plusieurs suites d'octets (caractère composé, ou « e » + accent combinant). La normalisation Unicode — str.normalize('NFKD') en Python — réduit ces variantes à une forme de référence. Ça ne couvre que l'encodage : pour le reste (orthographe d'époque, « eussent » là où l'on écrirait « auraient »…), la veille est formelle — aucun modèle public de post-correction OCR français n'existe ; on traite par règles + dictionnaires d'alias (nom canonique ↔ graphies observées), pas par un modèle. Les variantes d'orateurs deviennent des métadonnées filtrables, pas du texte à corriger.

La règle d'or : ne jamais écraser l'original

Pourquoi deux colonnes de texte, text_brut et text_normalise ?

Parce que les deux consommateurs n'ont pas les mêmes besoins. BM25 (la recherche lexicale, cf. leçon 0005) et l'authenticité des citations scientifiques exigent le texte d'origine ; l'embedding, lui, préfère la version nettoyée. PostgreSQL (colonnes multiples) comme Qdrant/OpenSearch (champs nommés multiples) permettent de stocker les deux. Voir axe1-donnees.md §1.1.

Le produit de cet étage est un format JSON canonique par intervention — la granularité de base de tout le pipeline :

{
  "id": "senat-1885-06-14-s001-i042",
  "date": "1885-06-14", "chambre": "senat", "session": "1885",
  "orateur": {"nom": "Victor Hugo"},
  "text_brut": "…", "text_normalise": "…",
  "page_jo": 612
}

Date, chambre, orateur, page du JO y vivent dans les métadonnées : c'est ce qui rendra possibles les facettes et les citations avec lien profond (leçon 0009, leçon 0008).

Objection légitime : une intervention isolée n'a de sens que rattachée aux autres. Pourquoi ce format « par intervention » alors ?

Parce que « par intervention » est la granularité d'indexation, pas l'unité de sens. Le lien est déjà dans le record — la clé de séance dans l'id, le rang de parole (i042) — et il se matérialise plus loin, au retrieval : on cherche le granulat, on restitue la séance parent (leçon 0002). Contrepartie assumée de l'enregistrement atomique : un batch idempotent ne réencode que ce qui a changé — un JSON « séance fourre-tout » rendrait tout recalcul solidaire. Les anaphores inter-interventions (« comme vient de le dire M. X »), elles, relèvent des patterns de contexte (fenêtre, agentique, graphe de suites de parole), pas du format de stockage.

Et les outils « tout fait » (Docling MIT, Tika, Unstructured) ? Utiles pour la forme et le chunking structurel, mais la veille conclut qu'il n'existe aucun outil dédié aux débats du XIXᵉ : l'étage de normalisation est maison, en Python pur.

À retenir. Normaliser pour chercher, jamais pour réécrire : text_brut pour citer, text_normalise pour encoder, alias en métadonnées.

Vérifiez que c'est acquis

1. Pourquoi conserver le texte OCR non corrigé à côté du texte normalisé ?

Exactement : text_brut nourrit BM25 et garantit des citations verbatim ; seule la version normalisée passe dans l'embedding. La taille d'index et les sauvegardes sont des effets de bord, pas la raison.

2. Comment la veille recommande-t-elle de traiter les variantes orthographiques des noms d'orateurs ?

Règles + dictionnaires (nom canonique ↔ graphies observées), stockés en métadonnées filtrables. La correction LLM n'est documentée que ciblée, sur les « pages chaudes » — jamais systématique sur tout le corpus.

Source principale : votre veille, axe 1 §1 ; côté outils : Docling, rapport technique (arXiv 2408.09869).
