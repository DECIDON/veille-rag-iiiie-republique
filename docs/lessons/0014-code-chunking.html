Étape 2 en code : découper par intervention, reconstituer la séance

À la fin de cette fiche, vous pouvez réécrire vous-même atelier/chunking.py : le script qui transforme les interventions normalisées en granulats indexables (les enfants) et en séances reconstituées (les parents), conformément au pattern parent-document de la leçon 0002.

Le principe de l'étape. L'unité de découpage n'est pas géométrique mais documentaire : une intervention égale un granulat, quitte à sous-découper les interventions fleuves en fragments numérotés. La séance entière est de son côté reconstituée en verbatim dans un fichier de parents, et seule la restitution affichera ce parent : on encode petit pour la précision du vecteur, on restitue large pour le contexte de la réponse.

Entrées et sorties

Le module lit data/normalise/interventions.jsonl (produit par l'étape 1) et écrit deux fichiers : data/enfants/enfants.jsonl, un enregistrement par granulat indexable, et data/parents/seances.jsonl, un enregistrement par séance. Tout le module ne dépend que de la bibliothèque standard (re et collections.OrderedDict) plus des deux fonctions JSONL importées de l'étape 1 :

from .normalisation import lire_jsonl, ecrire_jsonl

Compter les tokens sans tokenizer

Le plafond de taille d'un granulat se compte en tokens (les morceaux de mots que l'encodeur avalera), mais installer un tokenizer HuggingFace pour estimer une taille serait disproportionné. Le module retient un compteur de mots majoré de 30 %, suffisant pour encadrer la taille et sans dépendance :

def estimer_tokens(texte: str) -> int:
    """Estime des tokens par les mots (×1,3) ; suffisant pour encadrer la taille."""
    return max(1, round(len(texte.split()) * 1.3))

Le facteur 1,3 vient d'une observation simple : les tokeniseurs sous-word découpent les mots longs en plusieurs pièces, mais jamais moins d'une pièce par mot ; majorer le nombre de mots de 30 % donne une borne haute raisonnable pour du français. Ce n'est pas un comptage exact, et le module n'en demande pas davantage : le plafond de 1 200 tokens est une marge, pas une fenêtre glissante.

Découper : paragraphes, puis phrases, puis mots

La fonction decouper_texte applique un ordre de préférence explicite : garder des paragraphes entiers autant que possible, replier sur les phrases si un paragraphe dépasse le plafond, et ne couper « en monotone » (au mot près) qu'en dernier recours pour une phrase interminable. Les deux petites fonctions utilitaires définissent ce qu'est un paragraphe et ce qu'est une phrase :

def _paragraphes(texte: str) -> list[str]:
    return [p.strip() for p in re.split(r"\n\s*\n", texte) if p.strip()]

def _phrases(texte: str) -> list[str]:
    return [p.strip() for p in re.split(r"(?<=[.!?…:;])\s+", texte) if p.strip()]

Un paragraphe est ce que sépare une ligne vide (deux sauts de ligne, avec d'éventuels blancs entre les deux). Une phrase est ce qui suit un blanc après une ponctuation forte ; l'expression régulière (?<=[.!?…:;])\s+ utilise une réserve (le terme anglais est lookbehind, notée (?<=…)) : elle découpe avant le blanc uniquement si le caractère qui précède ce blanc est l'un de . ! ? … : ;. La ponctuation reste donc collée à sa phrase, ce qui rend les fragments relisibles.

Voici la fonction complète ; lisez-la comme une machine à états avec un tampon courant et une fonction de vidage basculer :

def decouper_texte(texte: str, max_tokens: int) -> list[str]:
    if estimer_tokens(texte) <= max_tokens:
        return [texte]                      # cas fréquent : rien à faire
    fragments: list[str] = []
    courant: list[str] = []

    def basculer() -> None:                 # vide le tampon dans les fragments
        nonlocal courant
        if courant:
            fragments.append("\n\n".join(courant))
            courant = []

    for para in _paragraphes(texte):
        if estimer_tokens(para) <= max_tokens:
            # le paragraphe tient-il dans le tampon déjà rempli ?
            if estimer_tokens("\n\n".join([*courant, para])) > max_tokens:
                basculer()
            courant.append(para)
            continue
        basculer()                          # sinon on vide, puis on découpe le paragraphe
        morceau: list[str] = []
        for phrase in _phrases(para):
            if morceau and estimer_tokens(" ".join([*morceau, phrase])) > max_tokens:
                fragments.append(" ".join(morceau))
                morceau = [phrase]
            else:
                morceau.append(phrase)
        if morceau:
            fragments.append(" ".join(morceau))
    basculer()

    finaux: list[str] = []                  # dernier recours : phrases interminables
    for frag in fragments:
        if estimer_tokens(frag) <= max_tokens:
            finaux.append(frag)
            continue
        mots = frag.split()
        taille = max(50, int(max_tokens / 1.3))
        for i in range(0, len(mots), taille):
            finaux.append(" ".join(mots[i:i + taille]))
    return finaux

Trois points de détail méritent l'attention. La jointure du tampon se fait avec "\n\n" entre paragraphes et avec un simple espace entre phrases : le fragment reste une suite naturelle de texte, pas un collage. Le tampon (ici la liste courant, vidée par basculer()) permet d'accumuler plusieurs petits paragraphes dans un même fragment plutôt que d'en produire une dizaine de minuscules. Enfin le dernier recours découpe au mot près avec taille = max(50, int(max_tokens / 1.3)) : on divise par 1,3 pour revenir de l'estimation aux mots, et le plancher de 50 mots évite une dégénérescence (une phrase dont chaque mot dépasserait l'estimation produirait des fragments d'un mot).

Cet ordre de préférence est un choix éditorial, et non une complexité gratuite : chaque niveau supplémentaire casse une frontière (paragraphe, puis phrase) que le texte offrait gratuitement. Le test test_decoupe_ne_perd_aucun_mot interdit justement l'accident le plus grave de tout découpage : qu'un mot disparaisse entre deux fragments.

De l'intervention au granulat enfant

Le parent d'une intervention se déduit de trois de ses champs — chambre, date, numéro de séance — et l'identifiant du parent se met au format où le numéro de séance est complété à gauche par des zéros (le terme anglais est zero padding), afin que le tri lexicographique des identifiants coïncide avec leur ordre chronologique :

def identifiant_seance(enreg: dict) -> str:
    """Identifiant déterministe du parent : chambre, date, numéro de séance."""
    return f"{enreg['chambre']}-{enreg['date']}-s{str(enreg['seance']).zfill(3)}"
    # ex. « senat-1922-11-28-s002 »

Chaque intervention devient alors un ou plusieurs granulats, dont l'identifiant porte un numéro de fragment (-c01, -c02…) et qui hérite de toutes les métadonnées utiles au filtrage et à la citation :

def enficher(enreg: dict, max_tokens: int = 1200) -> list[dict]:
    parent = identifiant_seance(enreg)
    fragments = decouper_texte(enreg["text_normalise"], max_tokens)
    enfants = []
    for rang, fragment in enumerate(fragments, start=1):
        enfants.append({
            "id": f"{enreg['id']}-c{rang:02d}",
            "intervention_id": enreg["id"],          # la vérité terrain compare ici
            "parent_id": parent,
            "chunk_index": rang, "chunk_total": len(fragments),
            "texte": fragment,
            "date": enreg["date"], "chambre": enreg["chambre"],
            "session": enreg["session"], "seance": enreg["seance"],
            "orateur": enreg["orateur"].get("nom_canonique", enreg["orateur"]["nom"]),
            "orateur_brut": enreg["orateur"]["nom"],
            "role": enreg["orateur"].get("role"),
            "groupe": enreg["orateur"].get("groupe"),
            "résumé": enreg.get("résumé"),
            "page_jo": enreg["page_jo"],
        })
    return enfants

Notez deux champs jumeaux : orateur porte le nom canonique (celui sur lequel on filtre et on compte) et orateur_brut le nom observé (celui que l'historien peut vouloir auditer). Notez aussi que le fragment encodé est tiré de text_normalise — décision de l'étape 1 — alors que la citation affichée viendra du parent, construit lui sur text_brut.

Le parent : la séance reconstituée en verbatim

Le pattern parent-document de la leçon 0002 promet que la réponse ramène la séance entière. Le module tient cette promesse sans framework : il regroupe les interventions par parent_id et les recoud en un document, dans l'ordre du fichier d'entrée, chacun préfacé par son orateur et sa page :

def seance_parent(interventions: list[dict]) -> dict:
    premiere = interventions[0]
    texte = "\n\n".join(
        f"### {e['orateur'].get('nom_canonique', e['orateur']['nom'])} — "
        f"page {e['page_jo']}\n\n{e['text_brut']}"        # verbatim : text_brut
        for e in interventions
    )
    return {
        "id": identifiant_seance(premiere),
        "date": premiere["date"], "chambre": premiere["chambre"],
        "session": premiere["session"], "seance": premiere["seance"],
        "intervenants": sorted({
            e["orateur"].get("nom_canonique", e["orateur"]["nom"]) for e in interventions
        }),
        "interventions": [e["id"] for e in interventions],
        "texte_reconstitue": texte,
    }

def etape2(config) -> tuple[int, int]:
    interventions = lire_jsonl(config.normalise_dir / "interventions.jsonl")
    enfants: list[dict] = []
    par_seance: "OrderedDict[str, list[dict]]" = OrderedDict()
    for enreg in interventions:
        enfants.extend(enficher(enreg, config.max_tokens_chunk))
        par_seance.setdefault(identifiant_seance(enreg), []).append(enreg)
    parents = [seance_parent(groupe) for groupe in par_seance.values()]
    ecrire_jsonl(enfants, config.enfants_path)
    ecrire_jsonl(parents, config.parents_path)
    return len(enfants), len(parents)

Le choix d'un OrderedDict (dictionnaire à ordre d'insertion) plutôt que d'un dict ordinaire est une assurance d'écriture : sur Python 3.7 et plus récents les deux se valent, mais le type annonce l'intention — les séances sont écrites dans l'ordre de leur première apparition, et le fichier de parents est reproductible à corpus constant. Le parent n'est jamais indexé dans la base vectorielle : il vit sur disque, et la recherche ne fait que le rattacher à ses enfants (page 0017).

Comment le module est testé

tests/test_02_chunking.py, exécuté par uv run -m pytest tests/test_02_chunking.py -v, affirme les comportements du contrat :

  • test_intervention_courte_un_seul_enfant : une intervention sous le plafond produit un granulat unique, chunk_total = 1.
  • test_intervention_longe_plusieurs_enfants_numerotes : au-dessus du plafond, les fragments sont numérotés et partagent le parent_id.
  • test_chaque_fragment_respecte_la_taille_maximale et test_decoupe_ne_perd_aucun_mot : la taille est bornée, rien ne se perd.
  • test_parent_reconstitue_la_seance : le parent regroupe les intervenants et l'inventaire des interventions.
  • test_identifiant_seance_complete_le_zero : « s002 » et non « s2 ».
  • test_etape2_complete_sur_corpus_fourni : 165 enfants et un seul parent sur le corpus d'exemple.

À vérifier de votre côté : après uv run python -m atelier chunker, data/enfants/enfants.jsonl compte 165 lignes et data/parents/seances.jsonl une seule (le corpus fourni est une séance unique, aucune intervention ne dépasse le plafond).

Vérifiez que c'est acquis

1. Pourquoi l'estimation des tokens est-elle un simple compteur de mots majoré de 30 % ?

Le plafond de 1 200 tokens est une marge de sécurité sur la taille des granulats, pas une fenêtre de tokenizer : une borne haute au 30 % suffit, et elle évite d'importer transformers dans une étape qui doit rester testable hors-ligne, sans dépendance ni poids.

2. Pourquoi decouper_texte préfère-t-il les paragraphes, puis les phrases, puis les mots ?

Le découpage géométrique n'intervient qu'en dernier recours, pour une phrase interminable. Un fragment qui s'arrête sur une frontière de paragraphe reste un tout lisible pour le cross-encoder comme pour l'œil ; c'est la traduction en code de la règle « frontières documentairement vraies avant d'être géométriques » (leçon 0002).

3. Pourquoi le texte du parent est-il construit sur text_brut et celui des enfants sur text_normalise ?

Les enfants sont la matière de l'embedding et doivent rencontrer la saisie de l'utilisateur (étape 1) ; le parent n'est jamais encodé, il est restitué à l'affichage, et une citation scientifique se doit verbatim — c'est-à-dire conforme à la page imprimée, accents et capitales d'origine inclus.
