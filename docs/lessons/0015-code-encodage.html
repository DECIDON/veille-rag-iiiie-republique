Étape 3 en code : encoder dense et sparse, avec un cache idempotent

À la fin de cette fiche, vous pouvez réécrire vous-même atelier/embedders.py et la fonction etape3_encoder de atelier/indexation.py : un encodeur qui sort de chaque granulat un vecteur dense de 1 024 dimensions et un vecteur sparse appris, et un cache qui ne recalcule jamais deux fois le même texte.

Le principe de l'étape. bge-m3 (MIT, 568 M de paramètres, conçu pour tourner sur CPU) fournit les deux bras de l'hybride dans un seul modèle : un vecteur dense (une liste de 1 024 nombres, qui capture le sens et la paraphrase) et un vecteur sparse appris (une carte « identifiant de jeton → poids lexical » qui joue le rôle d'un BM25 appris, fidèle au terme exact). L'encodage étant la partie chère de la chaîne, chaque vecteur est mis en cache sous une empreinte de (encodeur + texte) : le batch est idempotent et repreneable, comme l'exige la veille §7.

Le contrat que tous les encodeurs respectent

Le module définit deux classes et une fabrique. Les deux classes exposent le même petit contrat — c'est un seam (une couture) : la suite du pipeline ne connaît que ces quatre membres, jamais l'implémentation.

  • nom : une chaîne, intégrée à l'empreinte du cache (changer d'encodeur invalide tout le cache, et c'est voulu).
  • dim : la dimension des vecteurs denses (1 024 pour bge-m3 comme pour le dummy).
  • encode_dense(textes: list[str]) -> list[list[float]] : un vecteur normalisé par texte.
  • encode_sparse(textes: list[str]) -> list[dict[int, float]] : une carte jeton → poids, vide de tout zéro.
def creer(nom: str, device: str | None = None):
    """Fabrique l'encodeur demandé (``bge-m3`` ou ``dummy``)."""
    if nom == "dummy":
        return DummyEmbedder()
    if nom == "bge-m3":
        return BgeM3Embedder(device=device)
    raise ValueError(f"encodeur inconnu : {nom!r} (attendu « bge-m3 » ou « dummy »)")

DummyEmbedder : la plomberie hors-ligne

Le premier encodeur n'a aucune valeur sémantique : c'est un sac de mots haché, déterministe, sans téléchargement. Il sert aux tests d'intégration et au make smoke, jamais à une mesure de qualité. Sa lecture est instructive parce qu'il remplit le même contrat que le vrai modèle :

_MOTS = re.compile(r"[0-9a-zà-ÿ]+")

class DummyEmbedder:
    nom = "dummy"; dim = 1024

    @staticmethod
    def _hachage(mot: str) -> int:
        return int.from_bytes(
            hashlib.blake2b(mot.encode("utf-8"), digest_size=8).digest(), "big",
        )

    def encode_dense(self, textes):
        vecteurs = []
        for texte in textes:
            v = [0.0] * self.dim
            for mot in _MOTS.findall(texte.lower()):
                h = self._hachage(mot)
                v[h % self.dim] += 1.0 if (h >> 63) else -1.0   # signe = bit de poids fort
            norme = math.sqrt(sum(c * c for c in v)) or 1.0
            vecteurs.append([c / norme for c in v])
        return vecteurs

Chaque mot est haché en un entier de 64 bits ; le modulo dim choisit la case du vecteur dense, et le bit de poids fort (h >> 63) donne le signe, afin que deux mots différents ne s'additionnent pas toujours dans la même direction. La division finale par la norme euclidienne produit des vecteurs de norme 1, comparables par cosinus — la même propriété que les vrais embeddings. Côté sparse, le même hachage compte les occurrences sous l'identifiant h % 2³¹. Le but n'est pas la ressemblance avec bge-m3 : c'est de faire rouler cache, indexation, fusion et filtres à coût nul.

BgeM3Embedder : pourquoi pas sentence-transformers ?

Piège vérifié sur le terrain. On s'attend à charger bge-m3 par SentenceTransformer("BAAI/bge-m3"). Cela ne donne que la partie dense : la classe des modèles sparse de la bibliothèque (SparseEncoder, réservée à SPLADE & co) ignore la tête sparse de bge-m3, tout simplement parce qu'elle ne figure pas dans le fichier modules.json du dépôt. Le nom SparseTextEmbeddingModel que la première version de l'atelier importait n'a jamais existé dans sentence-transformers — l'import échouait en ImportError. Conséquence : le module charge le modèle en direct avec transformers et applique lui-même la formule officielle de la référence FlagEmbedding (BAAI), ce qui charge deux fois moins de poids en mémoire (2,3 Go au lieu de 4,6).

Le constructeur télécharge et prépare trois objets, avec un import différé pour que les tests unitaires n'exigent ni torch ni les poids :

class BgeM3Embedder:
    nom = "bge-m3"; dim = 1024
    MODELE = "BAAI/bge-m3"
    TETE_SPARSE = "sparse_linear.pt"
    MAX_JETONS = 512          # les granulats font ≤ 1 200 tokens ; garde-fou mémoire

    def __init__(self, device: str | None = None) -> None:
        import torch
        from huggingface_hub import hf_hub_download
        from transformers import AutoModel, AutoTokenizer

        self._device = device or ("cuda" if torch.cuda.is_available() else "cpu")
        self._tokeniseur = AutoTokenizer.from_pretrained(self.MODELE)
        self._modele = AutoModel.from_pretrained(self.MODELE).to(self._device).eval()
        # Tête sparse : un simple Linear(1 024 → 1) livré avec les poids.
        tete = torch.nn.Linear(self._modele.config.hidden_size, 1)
        tete.load_state_dict(
            torch.load(hf_hub_download(self.MODELE, self.TETE_SPARSE), map_location="cpu"),
        )
        self._tete_sparse = tete.to(self._device).eval()
        self._speciaux = frozenset(id_ for id_ in (...) if id_ is not None)  # cls/eos/pad/unk

Trois gestes demandent une explication. .eval() place le réseau en mode évaluation : les comportements propres à l'entraînement (abandon aléatoire de neurones dit dropout, mise à jour des statistiques de normalisation) se figent, sans quoi deux encodages du même texte pourraient donner deux vecteurs différents. torch.no_grad (plus bas) désactive le suivi des gradients, les calculs intermédiaires servant à l'apprentissage — l'atelier n'apprend rien, il infère. La tête sparse n'est qu'une couche linéaire de 1 024 entrées vers 1 sortie, soit ~4 kilo-octets : le fichier sparse_linear.pt du dépôt HuggingFace en fournit les poids, et c'est tout ce qu'il faut pour pondérer chaque jeton.

La passe unique qui alimente les deux bras

Les deux méthodes d'encodage partagent une même passe du transformeur, car un granulat ne doit traverser le modèle qu'une fois :

def _passe(self, textes: list[str]):
    """Une passe du transformeur : états cachés, ids des jetons, poids lexicaux."""
    torch = self._torch
    encodage = self._tokeniseur(
        textes, padding=True, truncation=True,
        max_length=self.MAX_JETONS, return_tensors="pt",
    ).to(self._device)
    with torch.no_grad():
        etats = self._modele(**encodage).last_hidden_state
        # poids par jeton : ReLU(Linear(h)) — la formule de la référence
        poids = torch.relu(self._tete_sparse(etats)).squeeze(-1)   # [lot, longueur]
    return etats, encodage["input_ids"], poids
  • padding=True remplit les textes courts pour qu'ils tiennent dans le même tenseur rectangulaire que le lot ; truncation=True borne chaque texte à 512 jetons et plafonne la mémoire. Le commentaire du module note que les granulats de l'atelier tiennent sous ce plafond ; si vos granulats approchaient la limite de 1 200 tokens estimés de l'étape 2, la troncature couperait leur fin sans avertir — à ce stade, relevez MAX_JETONS au prix de la mémoire, ou baissez max_tokens_chunk, et vérifiez sur un échantillon.
  • last_hidden_state est la suite des représentations contextuelles produites par la dernière couche : une matrice de longueur × 1 024 par texte, où chaque ligne correspond à un jeton.
  • Le choix de no_grad plutôt que d'inference_mode est délibéré, et le commentaire du code le dit : les tenseurs produits dans un bloc inference_mode deviennent inutilisables par certaines opérations en dehors du bloc ; no_grad leur laisse leur statut de tenseurs ordinaires.

Le bras dense est le plus simple des deux : il prend la ligne du jeton CLS (le jeton spécial de tête, position 0, dont le transformeur fait une résumé du texte entier) puis normalise à la norme L2 — c'est exactement la configuration modules.json que sentence-transformers applique à ce modèle :

def encode_dense(self, textes, batch_size: int = 16):
    vecteurs = []
    for debut in range(0, len(textes), batch_size):
        etats, _, _ = self._passe(list(textes)[debut:debut + batch_size])
        denses = torch.nn.functional.normalize(etats[:, 0], p=2, dim=1)  # CLS + L2
        vecteurs.extend([[float(x) for x in ligne] for ligne in denses])
    return vecteurs

La normalisation L2 (division par la longueur du vecteur) n'est pas un ornement : la collection Qdrant est déclarée en distance cosinus, et deux vecteurs normalisés se comparent par un simple produit scalaire. La boucle par lots de 16 borne l'empreinte mémoire : un passage de 40 000 granulats d'un coup exploserait la RAM.

Le bras sparse applique la formule de la référence FlagEmbedding, que le module reproduit à la main : poids par jeton ReLU(Linear(h)), maximum conservé par identifiant de jeton lorsque le jeton revient plusieurs fois, jetons spéciaux exclus :

def encode_sparse(self, textes, batch_size: int = 16):
    plonges = []
    for debut in range(0, len(textes), batch_size):
        _, ids, poids = self._passe(list(textes)[debut:debut + batch_size])
        for ligne_ids, ligne_poids in zip(ids.tolist(), poids.tolist()):
            v: dict[int, float] = {}
            for indice, p in zip(ligne_ids, ligne_poids):
                if indice in self._speciaux:
                    continue                     # cls/eos/pad/unk exclus
                if p > v.get(indice, 0.0):
                    v[indice] = p                # max par identifiant de jeton
            plonges.append(v)
    return plonges

La référence officielle fait cette réduction avec un scatter_reduce « amax » sur tenseur ; l'atelier la fait dans un dictionnaire Python pour deux raisons documentées dans le code : le scatter_reduce s'est révélé un no-op silencieux sur un build particulier de torch, et un dictionnaire sparse évite d'allouer un tenseur dense de 250 002 dimensions (la taille du vocabulaire) par ligne. Un incident de ce genre — une fonction qui ne plante pas mais ne fait rien — est précisément ce qu'un test de contrat vient surveiller (plus bas).

Le cache : une empreinte, un ajout, aucune recomputation

La fonction d'étape vit dans indexation.py (le même fichier qui enverra les vecteurs à Qdrant). Son mécanisme tient en une idée : un vecteur n'est recalculé que si son empreinte a changé, et l'empreinte mêle l'encodeur et le texte :

def _empreinte(texte: str, nom_encodeur: str) -> str:
    return hashlib.sha256(f"{nom_encodeur}\x00{texte}".encode("utf-8")).hexdigest()

def etape3_encoder(config, embedder=None) -> int:
    enfants = lire_jsonl(config.enfants_path)
    embedder = embedder or _emb.creer(config.embedder)
    cache = charger_cache(config.cache_path)          # dict id → entrée

    a_encoder = [
        e for e in enfants
        if cache.get(e["id"], {}).get("empreinte")
        != _empreinte(e["texte"], embedder.nom)       # nouveau ou modifié
    ]
    for debut in range(0, len(a_encoder), config.batch):
        morceau = a_encoder[debut:debut + config.batch]
        textes = [e["texte"] for e in morceau]
        denses = embedder.encode_dense(textes)
        sparse = embedder.encode_sparse(textes)
        for enfant, dense, plong in zip(morceau, denses, sparse):
            cache[enfant["id"]] = {
                "id": enfant["id"],
                "empreinte": _empreinte(enfant["texte"], embedder.nom),
                "dense": dense,
                "sparse": {str(k): float(v) for k, v in plong.items()},
            }
        print(f"encodé {min(debut + config.batch, len(a_encoder))}/{len(a_encoder)}")
    # … réécriture complète du fichier cache.jsonl …
    return len(a_encoder)

Quatre conséquences en découlent, à comprendre avant de copier. L'octet \x00 séparant l'encodeur du texte rend l'empreinte non ambiguë (sans lui, un encodeur nommé « bge- » et un texte commençant par « m3 » produiraient la même empreinte qu'un encodeur « bge-m3 » sur un texte vide). Le sélecteur cache.get(…).get("empreinte") != … traite le granulat jamais vu et le granulat dont le texte a changé par le même chemin — c'est ce qui rend la relance correcte après une modification du corpus, sans tout rejouer. Le fichier est réécrit intégralement à la fin, et non appendu : c'est simple, et cela purge les entrées orphelines ; à l'échelle des millions de chunks réels, on remplacerait ce geste par un append suivi d'un compactage périodique, ce que le fichier JSONL permet sans format binaire. Enfin le JSON n'admettant que des chaînes comme clés, les identifiants de jetons du sparse sont écrits str(k) et reconvertis à la lecture.

Le cache est volontairement un fichier texte et non une base : il se relit avec un éditeur, se diagnostique à la ligne, et la base vectorielle Qdrant reste la seule source de vérité indexée.

Comment le module est testé

tests/test_03_encodage.py (hors-ligne, encodeur dummy) vérifie le contrat plutôt que l'implémentation, ce qui laisse les deux classes libres d'évoluer :

  • test_dense_dimension_et_norme : dimension 1 024 et norme 1 à 10⁻⁵ près.
  • test_dense_deterministe_et_distinct : même texte deux fois donne même vecteur, deux textes différents donnent des vecteurs différents.
  • test_sparse_ids_positifs_et_poids_strictement_positifs : le squelette du contrat sparse.
  • test_cache_idempotent : deux passes d'etape3_encoder d'affilée recalculent 0 vecteur à la seconde.
  • test_contrat_bge_m3, marqué -m modele : rejoue le même contrat sur les vrais poids (~2,3 Go téléchargés une fois). C'est le test qui aurait attrapé le scatter_reduce muet.

À vérifier de votre côté : après uv run python -m atelier encoder, le fichier data/vecteurs/cache.jsonl existe avec 165 lignes ; une seconde exécution affiche 0 vecteurs calculés.

Vérifiez que c'est acquis

1. Pourquoi le module charge-t-il bge-m3 en direct avec transformers au lieu de sentence-transformers ?

sentence-transformers charge très bien le dense de bge-m3, mais sa classe sparse (SparseEncoder, pour SPLADE & co) ignore la tête sparse de ce modèle, absente de son modules.json. Le chargement direct reproduit exactement la même configuration dense (pooling CLS, normalisation L2) et applique à la main la tête sparse de la référence FlagEmbedding, avec un seul chargement des poids à la clé.

2. Que garantit l'empreinte sha256(encodeur + texte) du cache ?

Le cache est keyed (indexé) par empreinte : tant que l'encodeur et le texte ne bougent pas, le vecteur en cache reste valide ; si l'un change, l'empreinte change et le granulat rejoint la file de recalcul — et lui seul. C'est la définition même d'un batch idempotent et repreneable (veille §7).

3. Pourquoi le vecteur sparse omet-il les jetons spéciaux (cls, eos, pad, unk) ?

Un poids sparse sert à retrouver un terme. Or cls marque la tête de la séquence, pad remplit le bourrage, eos la termine : ils traduisent la géométrie du lot, pas le vocabulaire. La référence FlagEmbedding les écarte, la reproduction de la formule les écarte ; les conserver ajouterait du bruit au bras lexical.
