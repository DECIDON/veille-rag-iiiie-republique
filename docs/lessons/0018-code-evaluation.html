Étape 6 en code : le parseur de questions, les métriques, le double bilan

À la fin de cette fiche, vous pouvez réécrire vous-même atelier/evaluation.py : le parseur du fichier de questions, les deux métriques (recall@k et MRR), le double passage question réelle contre requête oracle, et la petite couture qui rend le tout testable sans Qdrant ni modèle.

Le principe de l'étape. Hors de la distribution du corpus, aucun classement public ne prédit la qualité de votre recherche : le seul juge est l'évaluation interne sur questions-réponses annotées à la main (veille §6.5). Le module ne « fait pas la recherche » : il reçoit une fonction recuperer(question, texte) → [intervention_id] que la ligne de commande lui injecte, joue les questions, compte les deux métriques. Cette inversion (l'évaluation commande, la recherche exécute) est ce qui permet de tester les métriques sur des palmarès fictifs, sans service.

Le fichier de questions est du Markdown, pas une base de données

Le jeu vit dans data/questions/QUERIES.md, un bloc Markdown par question, parce que le binôme qui l'annotera est un historien et non une interface. Le format voulu, tel que documenté dans l'en-tête du fichier :

## Q1 — quel texte ouvre la discussion (Sénat, 1922)
- question: ordre du jour séance section budget
- question_oracle: budget general exercice 1923 travaux publics 3e section aeronautique
- attendus: senat-1922-11-28-s002-i007
- filtres: chambre=senat; from=1922-11-01; to=1922-11-30

Quatre champs, chacun avec une raison d'être là. question est ce que taperait le chercheur : des mots-clés courts, dérivés du besoin seul. question_oracle est optionnel : la requête idéale telle que la connaît quelqu'un qui a déjà lu la réponse ; elle ne sert jamais de question, seulement de plafond de comparaison. attendus porte un ou plusieurs identifiants d'intervention (et non de granulat : l'évaluation compare sur intervention_id, pour que le découpage en fragments ne casse pas la vérité terrain). filtres applique les mêmes clés que la recherche. Le parseur tient en une fonction ; trois détails le rendent robuste au fichier réel :

BLOC = re.compile(r"^##\s+", re.MULTILINE)

@dataclass
class Question:
    id: str
    texte: str
    attendus: list[str]
    filtres: dict = field(default_factory=dict)
    oracle: str = ""

def parser_queries(chemin: Path) -> list[Question]:
    contenu = Path(chemin).read_text(encoding="utf-8")
    hors_barrieres, dans_barriere = [], False
    for ligne in contenu.splitlines():
        if ligne.lstrip().startswith("```"):
            dans_barriere = not dans_barriere       # les gabarits entre ``` sont ignorés
            continue
        if not dans_barriere:
            hors_barrieres.append(ligne)
    contenu = "\n".join(hors_barrieres)
    questions: list[Question] = []
    for bloc in BLOC.split(contenu)[1:]:
        lignes = bloc.splitlines()
        identifiant = lignes[0].split("—")[0].strip() if lignes else f"q{len(questions) + 1}"
        champs = {"question": "", "question_oracle": "", "attendus": "", "filtres": ""}
        for ligne in lignes:
            m = re.match(r"^\s*-\s*(question_oracle|question|attendus|filtres)\s*:\s*(.*)$", ligne)
            if m:
                champs[m.group(1)] = m.group(2).strip()
        if not champs["question"] or not champs["attendus"]:
            continue                                 # bloc commentaire ou exemple non validé
        attendus = [a.strip() for a in champs["attendus"].split(",") if a.strip()]
        filtres: dict = {}
        for paire in (f.strip() for f in champs["filtres"].split(";") if f.strip()):
            if "=" in paire:
                clef, valeur = paire.split("=", 1)
                filtres[clef.strip()] = valeur.strip()
        questions.append(Question(
            identifiant, champs["question"], attendus, filtres, champs["question_oracle"],
        ))
    return questions
  • Le fichier documente son propre gabarit en blocs de code ```markdown ; le parseur bascule un drapeau à chaque barrière et ignore tout ce qui est entre barrières — la documentation reste dans le fichier sans polluer l'évaluation.
  • La découpe des blocs se fait sur les titres ## ; l'identifiant de la question est ce qui précède le premier « — » du titre.
  • Un bloc sans question: ou sans attendus: est silencieusement ignoré : c'est ce qui permet au gabarit à copier (« ## Q_ — description du cas ») de rester dans le fichier.

Deux métriques, deux questions différentes

Le module ne calcule pour l'atelier ni nDCG (prévue quand le jeu approchera les 200 questions, selon la veille §6.5) ni aucune moyenne de scores : deux scalaires suffisent à piloter les arbitrages de l'atelier.

def rappel_attendus(attendus: list[str], retours: list[str]) -> float:
    """1.0 si au moins un attendu figure dans les retours, sinon 0.0."""
    ensemble_attendus = set(attendus)
    return 1.0 if ensemble_attendus & set(retours) else 0.0

def premier_rang(attendus: list[str], retours: list[str]) -> float:
    """MRR : 1 / rang du premier attendu retrouvé, 0 si aucun."""
    ensemble = set(attendus)
    for rang, identifiant in enumerate(retours, start=1):
        if identifiant in ensemble:
            return 1.0 / rang
    return 0.0

Le recall@k par question est binaire : la vérité terrain est-elle dans les k premiers ? Sa moyenne sur les questions répond à « le système est-il utilisable ? ». Le MRR (Mean Reciprocal Rank : moyenne de l'inverse du rang du premier attendu) répond à « à quelle place ? » : 1 si premier, 0,5 si second, 0,2 si cinquième. Le symbole & sur deux ensembles est leur intersection. Ces deux fonctions prennent des listes d'identifiants et rien d'autre : elles s'appellent donc sur un palmarès fictif dans un test unitaire, ce qui est tout l'objet du module.

Un seul point d'ancrage : la fonction injectée

evaluer et evaluer_compare ne connaissent ni Qdrant, ni encodeur, ni cross-encoder. Leur unique paramètre comportemental est recuperer(question, texte) → [intervention_id] :

def _executer(question: Question, recuperer, texte: str) -> dict:
    retours = recuperer(question, texte)
    return {
        "id": question.id, "texte": texte,
        "rappel": rappel_attendus(question.attendus, retours),
        "premier_rang": premier_rang(question.attendus, retours),
        "retours": retours,
    }

def evaluer(questions: list[Question], recuperer) -> dict:
    detail = [_executer(q, recuperer, q.texte) for q in questions]
    return {"detail": detail, **_agreger(detail)}   # rappel et mrr moyennés

La ligne de commande fabrique cette fonction fermée (une fonction qui capture son contexte) dans _evaluer, et c'est là que le pipeline réel apparaît :

def recuperer(q, texte: str) -> list[str]:
    nonlocal modele_rerank
    candidats = recherche.recherche_hybride(
        texte, encodeur, config, client, filtres=q.filtres,
    )
    if args.no_rerank:
        final = candidats[:args.k]
    else:
        if modele_rerank is None:                    # chargement unique du cross-encoder
            from sentence_transformers import CrossEncoder
            modele_rerank = CrossEncoder(config.reranker, device="cpu")
        final = recherche.reranker(texte, candidats, config, top_k=args.k,
                                   _modele=modele_rerank)
    return [r["intervention_id"] for r in final]     # la comparaison se fait sur ce champ

Notez le mot nonlocal et sa raison : modele_rerank vit dans la fonction englobante _evaluer, le mot-clé dit à Python d'utiliser cette variable-là et non d'en créer une locale ; le cross-encoder (quelques secondes de chargement) n'est donc chargé qu'une fois pour les 28 questions. Notez aussi que la fonction retourne des intervention_id extraits des payloads : un attendu peut être retrouvé par n'importe lequel des fragments de son intervention.

Le double bilan : question réelle contre requête oracle

Une question annotée par quelqu'un qui connaît la réponse triche malgré elle : elle contient les mots de la réponse, et une recherche qui la réussit ne prouve rien. Le module quantifie ce biais plutôt que de le nier :

def evaluer_compare(questions: list[Question], recuperer) -> dict:
    """Double passe : question réelle (``texte``) puis requête oracle (``oracle``)."""
    detail = []
    for question in questions:
        ligne = {"id": question.id, "reel": _executer(question, recuperer, question.texte)}
        ligne["oracle"] = (
            _executer(question, recuperer, question.oracle) if question.oracle else None
        )
        detail.append(ligne)
    reel = _agreger([l["reel"] for l in detail])
    lignes_avec_oracle = [l for l in detail if l["oracle"]]
    oracle = _agreger([l["oracle"] for l in lignes_avec_oracle]) if lignes_avec_oracle else None
    ecart = (
        {"recall": oracle["recall"] - reel["recall"], "mrr": oracle["mrr"] - reel["mrr"]}
        if oracle else None
    )
    return {"detail": detail, "reel": reel, "oracle": oracle, "ecart": ecart}

L'ecart (oracle moins réel) est le fameux « gap lexical » : il mesure la part de la performance imputable aux mots de la réponse glissés dans la question. Un écart fort dit que le système vit de la coïncidence lexicale et qu'il faudra travailler le rappel (plus de candidats, query rewriting, autre encodeur) ; un écart faible dit que la recherche tient sur le sens. Le bilan oracle ne porte que sur les questions qui ont un oracle — les autres n'entrent que dans le bilan réel —, et c'est _agreger (somme des binaires, divisée par le nombre de lignes) qui produit les deux paires {nb_questions, recall, mrr} que la commande imprime, question par question puis en résumé.

Comment le module est testé

tests/test_06_evaluation.py, hors-ligne et sans service : test_parser_des_blocs (le fichier réel du kit se parse), test_question_realiste_sans_fuite (le champ question d'une Q&R du corpus ne contient pas les mots de l'oracle — le garde-fou du biais est aussi une donnée de test), test_rappel_binaire et test_premier_rang (les métriques sur palmarès fictifs), test_bilan_aggegre_les_questions, test_compare_double_passe_et_ecart (le mécanisme complet avec une fonction recuperer factice qui renvoie un palmarès écrit à l'avance).

À vérifier de votre côté : uv run python -m atelier evaluer affiche une ligne par question (rappel et rang inverse des deux passes, écart) puis le résumé réel : recall@5 …, MRR … — oracle (…) : … — écart : ….

Vérifiez que c'est acquis

1. Pourquoi evaluation.py reçoit-il une fonction recuperer au lieu d'appeler recherche_hybride lui-même ?

C'est la couture (le « seam ») du module : la logique de notation est pure et testable sur palmarès fictifs ; l'accouplement à Qdrant et au rerank vit dans la commande _evaluer, qui injecte la vraie fonction. Le deuxième bénéfice énoncé est réel mais secondaire : le premier est la testabilité, exigence de tout l'atelier.

2. Que mesure l'écart entre les scores de la passe oracle et de la passe réelle ?

La perte de performance que le rerank inflige au système sur le corpus réel. La vitesse de réponse séparant la passe réelle de la passe oracle du corpus.

La requête oracle porte les mots-clés de la réponse : elle fixe le plafond atteignable par un système lexical. L'écart oracle-réel est ce que le système concède à l'absence de ces mots — le « gap lexical » qui décide s'il faut travailler le rappel avant l'interface.

3. Un attendu apparaît en 4ᵉ position : que valent les deux métriques pour cette question ?

Le rappel par question est binaire : un attendu dans les k retours vaut 1, où qu'il soit dans le top-k. Le MRR vaut l'inverse du rang du premier attendu : 1/4 = 0,25. C'est justement parce que les deux mesurent des choses différentes (présence, position) qu'on les affiche côte à côte.
