Axe 1 — Les données · atelier

Atelier pipeline : du texte OCR à la recherche hybride

À la fin de cet atelier, vous aurez monté de vos mains, en Python, le pipeline complet de la variante CPU de la veille : un texte OCR entre dans le dossier data/corpus/, une question en sort avec ses citations de page du Journal officiel — et chaque station de ce trajet possède son test automatique.

Ce que l'atelier met en jeu. Les six leçons de l'axe 1 deviennent six commandes : normalisation maison (leçon 0001), découpage par intervention avec parent-séance (leçon 0002), encodage dense et sparse par bge-m3 (leçon 0003), indexation Qdrant quantifiée int8 avec filtres de payload (leçon 0004), entonnoir hybride RRF puis rerank cross-encoder (leçon 0005), évaluation par recall@k et MRR sur questions annotées (le seul juge, §6.5 de la synthèse). La génération LLM par Ollama est l'étape bonus, conformément à la leçon 0006 : elle décore un retrieval qui tient déjà seul.

Le trajet que vous allez parcourir

data/corpus/*.json  (interventions OCR, votre format d'entrée)
   │  1 · normaliser      Python pur : NFKD, apostrophes, césures, alias d'orateurs
   ▼
data/normalise/interventions.jsonl   (text_brut intact + text_normalise)
   │  2 · découper        1 intervention = 1 granulat enfant ; 1 séance = 1 parent
   ▼
data/enfants/enfants.jsonl  +  data/parents/seances.jsonl
   │  3 · encoder         BAAI/bge-m3 (MIT, CPU) : vecteurs 1 024 d + sparse appris, en cache
   ▼
data/vecteurs/cache.jsonl
   │  4 · indexer         Qdrant (Apache-2.0) : vecteurs nommés, int8, filtres sur payload
   ▼
   │  5 · rechercher      dense ⊕ sparse → fusion RRF → rerank bge-reranker-v2-m3 → parent
   ▼
top-5 interventions citées (page JO) + rappel de la séance parent
   │  6 · évaluer         recall@k et MRR sur data/questions/QUERIES.md
   │  7 · générer (bonus) Ollama (MIT) + Qwen3-4B : synthèse qui ne cite que les extraits fournis

Briques et licences : exactement la variante CPU du §8 de votre veille (sentence-transformers Apache-2.0, bge-m3 MIT, Qdrant Apache-2.0, bge-reranker-v2-m3 Apache-2.0, Ollama MIT, Qwen Apache-2.0). Le passage GPU ne toucherait que deux constantes (Qwen3-Embedding-8B, Qwen3-Reranker-8B), et son bien-fondé se chiffre d'abord — leçon 0011.

Étape 0 — Installation et configuration

Prérequis : uv (qui installe et gère un Python 3.10 ou plus récent au besoin), Docker (pour Qdrant), environ 8 Go de RAM libres et ~4 Go de disque pour les deux modèles (bge-m3 et le reranker téléchargés au premier appel réel, mis en cache dans ~/.cache/huggingface).

cd docs/ateliers/axe1-pipeline
make setup         # uv sync : .venv + dépendances verrouillées uv.lock (sentence-transformers, qdrant-client, pytest)
make up          # démarre Qdrant mono-nœud (docker-compose.yml, port 6333, données dans un volume Docker nommé)
make test        # les tests unitaires doivent passer ici déjà, sans modèle ni service

Vérifications de l'étape 0 : uv run python -m atelier affiche l'aide des sept commandes ; http://localhost:6333/dashboard ouvre le tableau de bord de Qdrant (collection encore absente, c'est normal) ; make test se termine sans échec. Toutes les commandes Python de la leçon s'écrivent avec uv run (uv run python -m atelier …, uv run -m pytest …) : uv résout l'environnement .venv et ses dépendances verrouillées à chaque appel ; alternativement, source .venv/bin/activate dispense du préfixe. Les réglages se font par variables d'environnement (ATELIER_QDRANT_URL, ATELIER_EMBEDDER, ATELIER_RERANKER, OLLAMA_URL, OLLAMA_MODEL) — toutes détaillées dans le README de l'atelier.

Le garde-fou hors-ligne. Une variable ATELIER_EMBEDDER=dummy remplace bge-m3 par un sac de mots déterministe : la même plomberie (cache, indexation, fusion, filtres) roule sans télécharger deux gigaoctets. Elle sert aux tests d'intégration et à un make smoke de bout en bout ; elle ne doit jamais servir à mesurer une qualité de recherche, car ses vecteurs n'ont aucun sens.

Le format d'entrée que j'attends de vous

Un fichier JSON (tableau d'objets, ou JSONL) par lot de séances ; un objet = une intervention. Le contrat complet est dans data/corpus/README.md ; le voici :

{
  "id": "senat-1922-11-28-s002-i007",            // unique dans tout le dossier
  "date": "1922-11-28",                          // AAAA-MM-JJ
  "chambre": "senat",                            // "chambre" ou "senat", valeurs stables
  "session": "1922",
  "seance": "2",
  "résumé": "Le président ouvre la discussion sur le budget de l'aéronautique et des transports aériens", // court résumé de l'intervention
  "orateur": {"nom": "M. le président", "role": "président", "groupe": null},
  "text_brut": "… texte OCR SANS aucun nettoyage …",
  "page_jo": 1
}

Deux exigences découlent directement des leçons : ne pré-nettoyez rien (les césures, apostrophes et accents instables sont précisément la matière première de l'étape 1, leçon 0001) et gardez page_jo, car la citation de provenance se décide dès l'entrée des données (leçon 0008). Les noms d'orateurs se règlent par le dictionnaire data/corpus/alias_orateurs.json au format {"nom canonique": ["variantes observées"]}. Un corpus réel est fourni pour que tout roule avant vos données : la 2ᵉ séance du Sénat du 28 novembre 1922, budget de l'aéronautique — 165 interventions (data/corpus/brut/debats.json, converti en data/corpus/debats.converti.json).

Étape 1 — Normaliser (leçon 0001)

Commande : uv run python -m atelier normaliser. L'étage applique les règles annoncées par la veille : décomposition Unicode NFKD (forme stable qui conserve les accents), unification des apostrophes typographiques et des espaces insécables, rejointoiement des césures OCR (« insti-↵tution » redevient « institution », et « lec- ture » aussi quand l'export a aplati le saut de ligne en espace), aplatissement des blancs ; puis il ajoute orateur.nom_canonique via le dictionnaire d'alias. Il ne touche jamais au text_brut, qui reste la source des citations verbatim.

Tester : uv run -m pytest tests/test_01_normalisation.py -v — douze tests : apostrophes, césures, guillemets, intégrité de text_brut, alias, refus des enregistrements incomplets et des identifiants dupliqués. Vérifier : cent soixante-cinq lignes dans data/normalise/interventions.jsonl, chacune portant les deux versions du texte.

Étape 2 — Découper par intervention (leçon 0002)

Commande : uv run python -m atelier chunker. Chaque intervention devient un granulat enfant portant parent_id (la séance, identifiée par chambre + date + séance) ; une intervention dépassant ~1 200 tokens estimés est sous-découpée en fragments numérotés qui partagent le parent — les frontières restent documentairement vraies avant d'être géométriques. La séance entière est reconstituée dans data/parents/seances.jsonl, en verbatim : c'est ce parent qui sera restitué à l'affichage, la leçon 0002 l'exige.

Tester : uv run -m pytest tests/test_02_chunking.py -v — granulat unique pour une intervention courte, fragments numérotés au-delà du plafond, aucun mot perdu par la découpe, parent regroupant les intervenants. Vérifier : cent soixante-cinq enfants (aucune intervention du corpus fourni ne dépasse le plafond) et un seul parent, la séance unique.

Étape 3 — Encoder dense et sparse (leçon 0003)

Commande : uv run python -m atelier encoder. bge-m3 (MIT, 568 M de paramètres, CPU) produit par granulat un vecteur dense de 1 024 dimensions et un vecteur sparse appris ; la veille retient ce modèle précisément parce qu'un seul encodeur fournit les deux bras de l'hybride. Les vecteurs sont écrits dans un cache local keyed par empreinte (encodeur + texte) : une relance ne recalcule rien — le batch idempotent que la veille réclame pour l'indexation hors-ligne.

Tester : uv run -m pytest tests/test_03_encodage.py -v (dummy : contrat et idempotence) puis, une fois, uv run -m pytest -m modele pour valider le contrat sur les vrais poids bge-m3. Vérifier : une relance d'encoder affiche 0 vecteurs calculés.

Étape 4 — Indexer dans Qdrant (leçon 0004)

Commande : uv run python -m atelier indexer. La collection jo_debats est créée avec deux vecteurs nommés (dense, cosinus, quantifié int8 — la division par 4 de la mémoire de la leçon 0004 ; sparse), et des index de payload sur chambre, orateur, date, session, parent_id : le pouvoir de l'historien est la restriction, et elle doit rester chère à rien. Les identifiants de points sont des UUID dérivés (v5) des identifiants de granulat : réindexer deux fois ne duplique rien.

Tester : uv run -m pytest -m integration -v (Qdrant requis ; make test-complet) — collection quantifiée et sparse, index de payload présents, compte exact après deux passes. Vérifier : le tableau de bord http://localhost:6333/dashboard montre la collection et ses cent soixante-cinq points.

Étape 5 — Rechercher : l'entonnoir (leçon 0005)

Commande : uv run python -m atelier rechercher "budget general exercice 1923 travaux publics aeronautique" --chambre senat. Deux bras préfetchés (dense, sparse) remontent chacun 50 candidats sous le même filtre de payload ; la fusion RRF les combine par le rang (native côté serveur Qdrant, et implémentée côté client dans atelier/fusion.py pour être testable et extensible) ; le cross-encoder bge-reranker-v2-m3 ne relit que les 20 survivants et rend le top-5, chaque résultat ramenant sa séance parent.

Tester : uv run -m pytest tests/test_05_recherche.py -v — la formule RRF, le filtre construit, et (intégration) le bon document retrouvé puis l'exclusion effective de la chambre absente du corpus. Vérifier à l'œil : le top-1 de la commande ci-dessus est l'intervention du président ouvrant la discussion (…-i007), avec « page JO 1 » et la séance de rattachement.

Étape 6 — Évaluer sur questions-réponses (le seul juge)

Commande : uv run python -m atelier evaluer. Le fichier data/questions/QUERIES.md contient le format (une question de recherche, les identifiants d'intervention attendus, des filtres optionnels) et deux questions jouables sur le corpus fourni ; les 28 questions-réponses annotées du même corpus attendent dans data/questions/queries.json. L'évaluation affiche recall@k (la question est-elle rendue dans le top-k ?) et MRR (à quel rang apparaissent les attendus ?), puis la moyenne — les deux métriques de la veille §6.5, nDCG étant ajoutée quand le jeu comptera ses 200 questions.

Tester : uv run -m pytest tests/test_06_evaluation.py -v — parseur du fichier et métriques sur palmarès fictifs, sans service. À faire ensemble : les questions du corpus fourni sont annotées et ancrées verbatim dans data/questions/queries.json ; celles de vos corpus s'écriront à quatre mains dans une autre session, car une vérité terrain annotée par un non-historien ne vaut rien (leçon 0005).

Étape 7 (bonus) — Générer une synthèse citée (leçon 0006)

Ce n'est pas une étape du socle : la leçon 0006 recommande l'UX « retrieval-first ». Pour la jouer quand même : installez Ollama, tirez la variante hybride du modèle (~2,5 Go en Q4), et la commande s'insère après le rerank.

curl -fsSL https://ollama.com/install | sh     # Ollama (MIT)
ollama pull qwen3:4b-instruct                   # Apache-2.0, ~2,5 Go en GGUF Q4 — variante hybride, pas qwen3:4b (thinking-only, voir leçon 0006)
uv run python -m atelier generer "que dit montjou de l'infrastructure aeronautique a laval ?"

Le prompt système interdit toute information hors extraits et impose la citation de la page du Journal officiel ; si les extraits ne suffisent pas, le modèle doit répondre INSUFFISANT. Tester : uv run -m pytest -m reseau saute tant qu'Ollama n'est pas joignable, joue l'appel réel dès qu'il l'est. Latence attendue sur CPU seul : de l'ordre de la minute à froid — ce que la leçon 0006 annonçait, à condition d'avoir tiré la variante hybride ; avec le tag qwen3:4b (thinking-only), elle se compte en minutes et le délai est invisible (leçon 0006, « piège du tag ») ; la recherche, elle, répond en quelques dizaines de millisecondes.

Vérifiez que c'est acquis

1. Pourquoi l'étape 1 conserve-t-elle le texte brut intact à côté du texte normalisé ?

Le text_brut ne sert jamais à l'encodage : il fonde la recherche lexicale (dont les termes exacts de 1922) et garantit des citations verbatim ; le text_normalise seul passe dans l'embedding (leçon 0001, §1.1 de la veille).

2. Pourquoi découper par intervention plutôt que par découpage sémantique automatique ?

Séance, ordre du jour et intervention sont déjà marqués dans le Journal officiel : un découpage automatique redécouvre moins bien ce que le document dit (§2 de la veille). De plus, l'orateur — métadonnée de filtrage — est une propriété de l'intervention, donc la frontière utile est celle de l'intervention.

3. À quoi sert l'encodeur dummy de l'atelier ?

Ses vecteurs sont un sac de mots haché sans valeur sémantique : il vérifie cache, indexation, fusion et filtres à coût nul, et rien de plus. Toute mesure de qualité se fait sur bge-m3, et toute décision, sur vos Q&R (§6.5 de la veille).
