Axe 1 — Les données · atelier, étape 1

Étape 1 en code : normaliser le corpus, fonction par fonction

À la fin de cette fiche, vous pouvez réécrire vous-même atelier/normalisation.py et la charpente qui l'accueille : le script qui lit un corpus JSON d'interventions OCR et écrit, ligne par ligne, le fichier data/normalise/interventions.jsonl que toutes les étapes suivantes consommeront.

Le principe de l'étape. La normalisation produit un second texte, text_normalise, obtenu par règles déterministes, et elle laisse text_brut parfaitement intact : le texte brut nourrit la recherche lexicale et garantit des citations verbatim, le texte normalisé seul passera dans l'embedding (leçon 0001). Aucune bibliothèque tierce n'intervient ici — uniquement la bibliothèque standard de Python —, ce qui fait de ce module le plus portable et le plus testable de tout l'atelier.

La charpente commune à toutes les étapes

Avant la première règle de nettoyage, trois petits fichiers rendent le reste possible. Vous les écrivez une fois pour toute l'atelier.

1. Le squelette du paquet. Le répertoire atelier/ n'est un paquet (répertoire de modules Python importables) que parce qu'il contient un fichier __init__.py, et celui-ci ne porte que deux constantes de version. Comme le projet n'est pas installé (le fichier pyproject.toml porte package = false), la commande uv run python -m atelier normaliser exécute atelier/__main__.py depuis le répertoire de l'atelier, et les imports relatifs comme from . import normalisation résolvent dans ce même répertoire. Vous n'avez donc rien à installer d'autre que les dépendances pour que tout fonctionne.

2. config.py, toute la configuration en un objet immutable. Un dataclass (classe dont Python génère le constructeur) gelé par @dataclass(frozen=True) déclare les chemins et les réglages ; la fonction charger() en recopie un exemplaire avec les variables d'environnement appliquées, et le reste du code ne manipule que cet objet :

RACINE = Path(__file__).resolve().parent.parent   # dossier de l'atelier
DATA = RACINE / "data"

@dataclass(frozen=True)
class Config:
    qdrant_url: str = "http://localhost:6333"
    collection: str = "jo_debats"
    embedder: str = "bge-m3"        # "dummy" = plomberie hors-ligne
    dim: int = 1024                 # dimension des vecteurs de bge-m3
    max_tokens_chunk: int = 1200    # étape 2
    top_prefetch: int = 50          # étape 5 : candidats par bras
    top_fusion: int = 20            # étape 5 : survivants après RRF
    top_rerank: int = 5             # étapes 5-6 : résultats finaux
    rrf_k: int = 60                 # constante k de la fusion RRF
    batch: int = 16                 # étape 3 : textes par passe
    corpus_dir: Path = field(default_factory=lambda: DATA / "corpus")
    normalise_dir: Path = field(default_factory=lambda: DATA / "normalise")
    # … enfants_path, parents_path, cache_path, questions_path …

def charger() -> Config:
    defauts = Config()
    return replace(
        defauts,
        qdrant_url=os.environ.get("ATELIER_QDRANT_URL", defauts.qdrant_url),
        embedder=os.environ.get("ATELIER_EMBEDDER", defauts.embedder),
        # … chaque variable ATELIER_* ou OLLAMA_* avec son défaut …
    )

Trois décisions méritent d'être comprises avant d'être copiées. Le gel (frozen=True) rend toute modification accidentelle impossible en cours d'exécution. Les chemins sont déclarés avec field(default_factory=lambda: …), ce qui évalue le chemin à chaque construction de l'objet plutôt qu'à la définition de la classe — la précaution est gratuite et elle garde la porte ouverte à une configuration dont la racine changerait. Enfin, charger() applique les variables d'environnement en un seul endroit : un module qui a besoin du réglage reçoit un objet Config, jamais il ne lit os.environ lui-même, et un test peut donc injecter une configuration factice.

3. __main__.py, la répartition des commandes. Le module construit un argparse.ArgumentParser, déclare une sous-commande par étape, puis important le module demandé seulement quand la commande le réclame :

sous = parser.add_subparsers(dest="commande")
sous.add_parser("normaliser", help="étape 1 — corpus JSON → interventions normalisées")
# … chunker, encoder, indexer, rechercher, evaluer, generer …
args = parser.parse_args(argv)
config = _config.charger()

if args.commande == "normaliser":
    from . import normalisation            # import différé
    n = normalisation.etape1(config)
    print(f"{n} interventions normalisées → …")
    return 0

L'import différé (écrire l'import dans le if plutôt qu'en tête de fichier) n'est pas une coquetterie : la commande normaliser ne doit jamais échouer parce que qdrant-client ou torch (les bibliothèques lourdes des étapes 4 et 3) manquent. La fonction appelée porte un nom uniforme, etape1, etape2… : elle prend la configuration, écrit ses fichiers et renvoie le nombre d'enregistrements produits, ce qui est tout ce que la ligne de commande a besoin de savoir.

Le contrat d'entrée et sa validation

Le module fixe d'abord ce qu'un enregistrement valide doit contenir. Un objet JSON représentant une intervention doit porter ces champs, sous peine de refus :

CHAMPS_REQUIS = (
    "id", "date", "chambre", "session", "seance", "orateur", "text_brut", "page_jo",
)
_DATE = re.compile(r"\d{4}-\d{2}-\d{2}")

def valider(enreg: dict) -> None:
    manquants = [c for c in CHAMPS_REQUIS if c not in enreg or enreg[c] in (None, "")]
    if manquants:
        apercu = json.dumps(enreg, ensure_ascii=False)[:160]
        raise ValueError(f"enregistrement invalide (champs requis absents : "
                         f"{', '.join(manquants)}) — {apercu}")
    orateur = enreg["orateur"]
    if not isinstance(orateur, dict) or not orateur.get("nom"):
        raise ValueError(f"champ « orateur » attendu comme objet avec une clé « nom » : {orateur}")
    if not _DATE.fullmatch(str(enreg["date"])):
        raise ValueError(f"champ « date » attendu au format AAAA-MM-JJ : {enreg['date']}")

Deux détails de fabrication rendent l'erreur exploitable le jour où un export de 40 000 lignes sera mal formé : le message cite les champs manquants et un aperçu de 160 caractères de l'enregistrement fautif, et la date est vérifiée par expression régulière (mot à mot : quatre chiffres, deux chiffres, deux chiffres, séparés par des tirets) parce que tout le filtrage par plage de dates repose sur un tri lexicographique correct, ce que seul garantit le format ISO AAAA-MM-JJ. La validation refuse aussi l'identifiant vide, parce qu'un identifiant absent est exactement aussi grave qu'un identifiant faux : il casse la citation de provenance.

Le chargement accepte deux écritures — un fichier .json contenant un tableau ou un objet unique, et un fichier .jsonl (JSON Lines) contenant un enregistrement par ligne — et il refuse tout identifiant rencontré deux fois :

def charger_corpus(dossier: Path) -> list[dict]:
    enregistrements: list[dict] = []
    for chemin in sorted(dossier.glob("*.json")):
        if chemin.name == "alias_orateurs.json":
            continue                       # ce fichier-là n'est pas du corpus
        données = json.loads(chemin.read_text(encoding="utf-8").strip())
        if isinstance(données, list):
            enregistrements.extend(données)
        elif isinstance(données, dict):
            enregistrements.append(données)
    # … mêmes règles pour *.jsonl, une ligne = un json.loads …
    vus: set[str] = set()
    for enreg in enregistrements:
        identifiant = enreg.get("id")
        if identifiant in vus:
            raise ValueError(f"identifiant dupliqué dans le corpus : {identifiant}")
        vus.add(identifiant)
    return enregistrements

Le tri des chemins (sorted(glob(…))) rend l'ordre des fichiers déterministe, donc la sortie reproductible. Le refus des doublons se fait ici, à l'entrée, plutôt qu'à l'indexation : l'étape 4 dérivera l'identifiant du point Qdrant à partir de cet id, et deux interventions portant le même identifiant écriraient l'une sur l'autre en silence, sans aucun moyen de le remarquer plus tard.

normaliser_texte : sept règles, dans un ordre qui compte

Cœur du module, la fonction applique sept transformations dans un ordre précis ; chaque règle prépare la suivante.

def normaliser_texte(texte: str) -> str:
    t = texte
    # 1. toutes les variantes d'espace deviennent l'espace ASCII
    for espace in ("\u00a0", "\u202f", "\u200a", … , "\u2000"):
        t = t.replace(espace, " ")
    # 2. suppression des traits d'union mous (artefacts d'import Word/OCR)
    t = t.replace("\u00ad", "")
    # 3. rejointoiement des césures : « insti-\ntution » → « institution »
    t = _CESURE.sub(r"\1", t)
    # 4. unification des apostrophes sur l'apostrophe ASCII
    t = _APOSTROPHES.sub("'", t)
    # 5. unification des guillemets (les français « … » perdent leurs espaces)
    t = re.sub(r"\u00ab[ \u00a0]*", '"', t)
    t = re.sub(r"[ \u00a0]*\u00bb", '"', t)
    # 6. NFKD puis NFC (voir le paragraphe ci-dessous)
    t = unicodedata.normalize("NFKD", t)
    t = unicodedata.normalize("NFC", t)
    # 7. aplatissement des blancs
    t = re.sub(r"[ \t]+", " ", t)
    t = re.sub(r" ?\n ?", "\n", t)
    t = re.sub(r"\n{3,}", "\n\n", t)
    return t.strip()

La règle 3 mérite une lecture attentive, car c'est la seule dont l'écriture est délicate. Une césure OCR est un mot coupé par un trait d'union en fin de ligne ; selon l'outil d'export, la fin de ligne est restée un vrai saut de ligne (« insti-↵tution ») ou a été aplatie en un simple espace (« lec- ture »). L'expression régulière doit rattraper les deux sans jamais coller les mots d'un trait d'union légitime :

_CESURE = re.compile(
    r"([A-Za-zÀ-ÿà-ÿ])-(?:[ \t\r]*\n[ \t]*|[ \t]+)(?=[A-Za-zÀ-ÿà-ÿ])"
)
  • ([A-Za-zÀ-ÿà-ÿ]) capture la lettre qui précède le trait d'union, et sera réinjectée par \1 dans la substitution.
  • (?:[ \t\r]*\n[ \t]*|[ \t]+) est un groupe non capturant à deux branches : une fin de ligne (spaces et retour chariot tolérés autour) ou au moins un espace ou une tabulation. Un trait d'union collé à la lettre suivante, comme dans « garde-chasse », ne correspond donc jamais au motif, et les composés légitimes survivent.
  • (?=[A-Za-zÀ-ÿà-ÿ]) est une avance (le terme anglais est lookahead) : elle exige qu'une lettre suive, sans la consommer. Le motif ne rejointe donc jamais un trait d'union suivi d'une ponctuation ou d'un chiffre. La règle assume en revanche sa limite : une césure est par définition un trait d'union suivi d'une lettre, et un composé écrit avec espace dans un export aplati (« garde- chasse ») est indiscernable d'une vraie césure. Sur un corpus OCR, l'hypothèse de la césure est la plus fréquente, et une soudure occasionnelle coûte moins qu'un mot scindé introuvable par les deux recherches.

La règle 6, maintenant, est la seule qui n'est pas une simple substitution. Un même caractère affiché peut exister sous plusieurs suites de points de code Unicode : un « é » peut être un seul caractère précomposé ou un « e » suivi d'un accent aigu combinant ; une ligature « ﬁ » peut exister en un seul caractère de compatibilité. La bibliothèque standard offre deux formes de normalisation : NFKD (décomposition, forme « K » pour compatibilité, « D » pour décomposée) décompose tout ce qui peut l'être, ligatures comprises, et NFC (forme stable recomposée) recompose ensuite les accents en caractères précomposés, lisibles et comparables en Python comme en JSON. L'enchaînement NFKD→NFC est donc le geste standard : plier les compatibilités indésirables, rendre aux accents leur forme canonique. Une normalisation à une seule forme aurait un défaut : garder la forme décomposée (NFD seul) rend le texte illisible dans un éditeur et fausse la comparaison avec la saisie clavier de l'utilisateur.

Les règles 1, 4, 5 et 7 relèvent du même principe : l'OCR d'un journal du XIXᵉ siècle produit plusieurs signes graphiquement identiques (dix variantes d'apostrophe, douze variantes d'espace, les guillemets français avec leurs espaces insécables). Tout ce qui est encodé différemment de la saisie de l'utilisateur ne sera jamais retrouvé par aucune des deux recherches, lexicale ou vectorielle ; l'unification n'est donc pas un détail cosmétique, c'est la condition de la rencontre.

Les alias d'orateurs : la métadonnée, pas la correction

Le fichier data/corpus/alias_orateurs.json est un dictionnaire {"nom canonique": ["variantes observées"]}. Deux fonctions le rendent utilisable. La première fabrique une clé de comparaison robuste : minuscules, accents supprimés, apostrophes supprimées, ponctuation réduite à des tirets.

def cle_alias(nom: str) -> str:
    n = normaliser_texte(nom).replace("'", "")
    n = unicodedata.normalize("NFD", n.lower())
    n = "".join(c for c in n if not unicodedata.combining(c))   # retire les accents
    n = re.sub(r"[^a-z0-9]+", "-", n)
    return n.strip("-")

def charger_alias(chemin: Path) -> dict[str, str]:
    if not chemin.exists():
        return {}
    table_brute = json.loads(chemin.read_text(encoding="utf-8"))
    table: dict[str, str] = {}
    for canonique, variantes in table_brute.items():
        for variante in [canonique, *(variantes or [])]:
            table[cle_alias(variante)] = canonique
    return table

La suppression des accents s'appuie sur une propriété d'Unicode : la forme NFD sépare une lettre accentuée en la lettre de base plus un caractère combinant (l'accent, qui ne s'affiche que combiné à sa lettre) ; filtrer les caractères combinants laisse donc les lettres nues. La clé obtenue traite « Jean Jaurès », « Jean Jaures » et « JAURES, Jean » comme la même personne, pour peu que ces variantes figurent dans le dictionnaire.

La seconde fonction retourne {clé: nom canonique}, et l'enrichissement n'est qu'un regard dans cette table, avec repli sur le nom observé :

def normaliser_enregistrement(enreg: dict, alias: dict[str, str]) -> dict:
    valider(enreg)
    orateur = dict(enreg["orateur"])            # copie : on ne mute pas l'entrée
    nom = str(orateur["nom"])
    orateur["nom_canonique"] = alias.get(cle_alias(nom), nom)
    return {
        **enreg,
        "orateur": orateur,
        "text_normalise": normaliser_texte(str(enreg["text_brut"])),
    }

Notez le geste d'architecture, exactement celui de la leçon 0001 : l'alias ne réécrit jamais le texte de l'intervention, il ajoute une métadonnée filtrable (nom_canonique) à côté du nom observé. Un historien qui veut compter les prises de parole de Jaurès filtrera sur la métadonnée unifiée, et non sur une chaîne de caractères incertaine ; la variante d'OCR reste visible et auditable.

La sortie JSONL, réutilisée par toutes les étapes

Le module expose deux fonctions de lecture-écriture que les étapes 2, 3, 4 et 5 importeront telles quelles :

def ecrire_jsonl(enregistrements: list[dict], chemin: Path) -> None:
    chemin.parent.mkdir(parents=True, exist_ok=True)
    with chemin.open("w", encoding="utf-8") as flux:
        for enreg in enregistrements:
            flux.write(json.dumps(enreg, ensure_ascii=False) + "\n")

def lire_jsonl(chemin: Path) -> list[dict]:
    if not Path(chemin).exists():
        raise FileNotFoundError(f"{chemin} absent — lancer l'étape qui le produit d'abord")
    return [json.loads(ligne) for ligne in
            Path(chemin).read_text(encoding="utf-8").splitlines() if ligne.strip()]

def etape1(config) -> int:
    bruts = charger_corpus(config.corpus_dir)
    alias = charger_alias(config.corpus_dir / "alias_orateurs.json")
    enrichis = [normaliser_enregistrement(e, alias) for e in bruts]
    ecrire_jsonl(enrichis, config.normalise_dir / "interventions.jsonl")
    return len(enrichis)

Trois raisons au format JSONL (une ligne, un enregistrement) plutôt qu'un grand tableau : un fichier d'un million d'interventions se lit à la ligne près sans tout charger en mémoire, une ligne se relit même si le fichier est tronqué, et ensure_ascii=False écrit les accents en UTF-8 lisibles plutôt qu'en séquences \u00e9 illisibles à l'œil. Le point d'entrée etape1 montre le gabarit que toute étape de l'atelier respectera : lire en amont, transformer en mémoire par une fonction pure (une fonction dont le résultat ne dépend que de ses arguments), écrire en aval, renvoyer le compte.

Comment le module est testé

tests/test_01_normalisation.py contient treize tests, exécutés hors-ligne par uv run -m pytest tests/test_01_normalisation.py -v. Les noms disent l'affirmation, et c'est vous qui les écrirez si vous refaites le module :

  • test_apostrophes_unifiees_accentes_conservés et test_apostrophe_aigu_devenue_ascii vérifient la règle 4 ; test_tilde_et_espaces_insécables la règle 1.
  • test_césure_rejointée_pas_les_vrais_tirets et test_césure_aplatis_en_espace_rejointée exercent les deux branches de _CESURE.
  • test_texte_brut_jamais_écrasé compare l'enregistrement de sortie au corpus d'entrée : le moindre changement dans text_brut fait échouer le test.
  • test_alias_orateurs et test_nom_canonical_ajouté exercent la table d'alias ; test_validation_refuse_champs_manquants, test_validation_refuse_date_non_iso et test_charger_corpus_refuse_doublons vérifient les refus.
  • test_etape1_complete_sur_corpus_fourni relance tout le module sur le corpus d'exemple.

À vérifier de votre côté : après uv run python -m atelier normaliser, le fichier data/normalise/interventions.jsonl compte 165 lignes (le corpus fourni), et chaque ligne porte à la fois text_brut et text_normalise.

Vérifiez que c'est acquis

1. Pourquoi la normalisation enchaîne-t-elle NFKD puis NFC plutôt que de s'arrêter à NFKD ?

NFKD plie les ligatures et les espaces de compatibilité mais laisse les accents décomposés ; NFC recompose les accents en caractères précomposés. Sans cette seconde passe, « é » du corpus et « é » du clavier de l'utilisateur seraient deux suites de points de code différentes, et aucune recherche ne les reconcilierait.

2. Pourquoi l'alias d'un orateur ajoute-t-il nom_canonique sans corriger le texte ni le champ orateur.nom ?

L'historien filtre sur la métadonnée unifiée (« tous les discours de Jaurès, sous quelque graphie que l'OCR l'ait rendue ») et la source reste auditable telle quelle. Écraser le texte reviendrait à corriger le document, ce que la leçon 0001 refuse : seul text_normalise est transformé, et jamais text_brut.

3. Que se passerait-il si le module tolérait deux interventions portant le même id ?

L'identifiant de point Qdrant est dérivé de l'id par UUID v5 (page 0016) : deux interventions homoglyphes occuperaient le même point, la seconde écraserait la première, et aucune alerte ne serait jamais émise. Le refus à l'entrée coûte trois lignes ; le découvrir après coup coûte une ré-indexation.
