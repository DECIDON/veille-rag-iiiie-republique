Étape 5 en code : l'entonnoir, de la question au parent restitué

À la fin de cette fiche, vous pouvez réécrire vous-même atelier/fusion.py et atelier/recherche.py : deux bras prefetch sous le même filtre, fusion RRF (par Qdrant ou par votre propre fonction), rerank cross-encoder sur les survivants, et rattachement du parent-séance.

Le principe de l'étape. La leçon 0005 décrit un entonnoir : chaque étage est moins cher et plus exigeant que le précédent. Les deux bras (dense et sparse) remontent chacun 50 candidats sous le même filtre ; la fusion RRF (Reciprocal Rank Fusion) les combine par le rang et n'en garde que 20 ; le cross-encoder ne relit que ces 20 paires (question, fragment) et rend le top-5 ; enfin chaque résultat ramène sa séance parent. Les scores des deux bras ne se comparent pas — c'est le rang qui sert de dénominateur commun.

La fusion RRF, en vingt lignes testables

Qdrant sait fusionner lui-même ses bras prefetchs. L'atelier implémente pourtant la fusion en Python (atelier/fusion.py) pour trois raisons : rendre le mécanisme testable sans service, documenter la formule, et pouvoir fusionner plus tard un troisième bras qui ne viendrait pas de Qdrant (un BM25 d'OpenSearch, par exemple). La formule et son unique fonction :

score(doc) = Σ  1 / (k + rang(source, doc))      k = 60 par convention

def rrf(classements: list[list[str]], k: int = 60) -> list[tuple[str, float]]:
    """Fusionne des classements (listes d'identifiants, du mieux noté au moins
    bien noté) et retourne [(id, score_rrf), …] trié par score décroissant."""
    scores: dict[str, float] = {}
    for classement in classements:
        for rang, doc_id in enumerate(classement, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rang)
    return sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))

Lisons la formule plutôt que le code. Un document classé 1ᵉʳ dans un bras marque 1/(60+1) ≈ 0,0164 ; classé 50ᵉ dans l'autre, il marque 1/(60+50) ≈ 0,0091 ; et ces contributions s'additionnent, si bien qu'un document medium des deux bras déborde un champion isolé d'un seul bras. C'est exactement la vertu annoncée : la fusion récompense l'accord des deux recherches plutôt que la performance isolée de l'une d'elles. La constante k = 60 est la convention du papier d'origine de RRF ; elle aplatit les écarts de tête de classement, ce qui évite qu'une première place sur un seul bras écrase tout le reste. Le tri final départage à score égal par l'identifiant croissant, afin que la sortie soit déterministe alors que la table de hachage des scores ne l'est pas.

Construire le filtre de payload

La ligne de commande accepte des options simples (--chambre, --orateur, --from, --to, --session) que construire_filtre traduit en objets du client. Un dictionnaire Python simple sert de langage intermédiaire entre la commande et la requête, et les fonctions d'évaluation réutiliseront ce même dictionnaire (page 0018) :

def construire_filtre(filtres: dict):
    from qdrant_client.models import (
        DatetimeRange, FieldCondition, Filter, MatchValue,
    )
    conditions = []
    if "chambre" in filtres:
        conditions.append(FieldCondition(key="chambre", match=MatchValue(value=filtres["chambre"])))
    if "orateur" in filtres:
        conditions.append(FieldCondition(key="orateur", match=MatchValue(value=filtres["orateur"])))
    if "session" in filtres:
        conditions.append(FieldCondition(key="session", match=MatchValue(value=str(filtres["session"]))))
    if "from" in filtres or "to" in filtres:
        conditions.append(FieldCondition(
            key="date",
            range=DatetimeRange(gte=filtres.get("from"), lte=filtres.get("to")),
        ))
    return Filter(must=conditions) if conditions else None

Le mot must signifie la conjonction : toutes les conditions doivent être vraies. Une plage bornée inférieurement seulement (--from sans --to) s'écrit naturellement, DatetimeRange acceptant les bornes manquantes. Sans condition, la fonction retourne None et la requête n'est pas filtrée ; le test test_construire_filtre_vide_retourne_none surveille précisément cette absence : un Filter(must=[]) vide n'a pas partout la même signification qu'une absence de filtre.

Les deux bras, puis la fusion — côté serveur d'abord

Chaque bras est un Prefetch : une sous-requête dont Qdrant garde la liste avant de fusionner. La seule différence entre les deux est l'encodage de la question et le nom du vecteur interrogé :

def _requete_bras(quest_id: str, question: str, embedder, config, filtre):
    from qdrant_client.models import Prefetch
    if quest_id == "dense":
        vecteur = embedder.encode_dense([question])[0]
        return Prefetch(
            query=vecteur, using="dense", limit=config.top_prefetch, filter=filtre,
        )
    from qdrant_client.models import SparseVector
    plonges = embedder.encode_sparse([question])[0]
    return Prefetch(
        query=SparseVector(indices=list(map(int, plonges)), values=list(plonges.values())),
        using="sparse", limit=config.top_prefetch, filter=filtre,
    )

def recherche_hybride(question, embedder, config, client,
                      filtres=None, fusion="serveur"):
    from qdrant_client.models import Fusion, FusionQuery
    filtre = construire_filtre(filtres or {})
    bras = [_requete_bras(n, question, embedder, config, filtre) for n in ("dense", "sparse")]

    if fusion == "serveur":
        reponse = client.query_points(
            collection_name=config.collection,
            prefetch=bras,
            query=FusionQuery(fusion=Fusion.RRF),
            limit=config.top_fusion,
            with_payload=True,
        )
        return [p.payload for p in reponse.points]

Le filtre est passé dans chaque bras prefetch : Qdrant ne retient que les points admissibles avant de rapprocher les vecteurs, ce qui est la promesse du pré-filtrage vu à l'étape 4. Un seul appel réseau fait tout l'étage : deux ANN concurrentes, fusion RRF serveur, tronçage à top_fusion = 20. L'option --fusion locale de la ligne de commande emprunte l'autre chemin, visible dans le même module :

    # Fusion locale : deux ANN séparées puis RRF côté client (atelier.fusion).
    classements, payloads = [], {}
    for bras_q in bras:
        reponse = client.query_points(
            collection_name=config.collection,
            query=bras_q.query, using=bras_q.using,
            query_filter=filtre, limit=config.top_prefetch, with_payload=True,
        )
        classements.append([p.payload["chunk_id"] for p in reponse.points])
        for p in reponse.points:
            payloads[p.payload["chunk_id"]] = p.payload
    fusionnes = rrf(classements, k=config.rrf_k)
    return [payloads[d] for d, _ in fusionnes[:config.top_fusion]]

Les deux chemins doivent converger, et cette convergence est un test en soi (ici, deux tests d'intégration vérifient que le bon document ressort des deux manières). La version locale est plus bavarde en réseau mais rend la fusion observable et modifiable — c'est le « seam » revendiqué par l'en-tête du module.

Le rerank : relire 20 paires, pas 15 millions

def reranker(question, candidats, config, top_k=None, _modele=None):
    """Rerank cross-encoder sur les candidats fusionnés ; tri par score rerank."""
    from sentence_transformers import CrossEncoder
    modele = _modele or CrossEncoder(config.reranker, device="cpu")
    paires = [(question, c["texte"]) for c in candidats]
    scores = modele.predict(paires)
    classes = sorted(zip(candidats, scores), key=lambda cs: -cs[1])
    final = []
    for candidat, score in classes:
        copie = dict(candidat)
        copie["score_rerank"] = float(score)
        final.append(copie)
    return final[:top_k or config.top_rerank]

Un cross-encoder n'encode pas deux objets séparés : il lit la question et le fragment ensemble et produit un score de pertinence — c'est ce qui le rend nettement plus juste et nettement plus cher qu'un bi-encodeur, d'où l'entonnoir qui ne lui livre que 20 candidats. Le paramètre _modele permet à l'appelant de passer un modèle déjà chargé : le chargement de bge-reranker-v2-m3 coûte quelques secondes, et l'évaluation (étape 6) le charge une fois pour ses 28 questions plutôt qu'une fois par question. Le score brut est conservé dans score_rerank : un audit de réponse doit pouvoir dire pourquoi tel fragment est premier.

Restituer le parent, afficher la preuve

def charger_parents(chemin) -> dict[str, dict]:
    if not Path(chemin).exists():
        return {}
    return {p["id"]: p for p in lire_jsonl(chemin)}

def restituer_parents(resultats, parents):
    """Attache le parent (séance reconstituée) à chaque résultat, sans le dupliquer."""
    for resultat in resultats:
        resultat["parent"] = parents.get(resultat.get("parent_id") or "")
    return resultats

Le parent n'est pas copié dans chaque résultat mais référencé depuis une table chargée une fois depuis data/parents/seances.jsonl : cinq résultats d'une même séance ne pèsent pas cinq fois la séance. L'affichage (afficher) met alors en forme une réponse « retrieval-first » : rang, orateur, chambre, date, page du Journal officiel, identifiant du granulat, extrait tronqué à 320 caractères, score de rerank signé, et le parent avec son compte d'interventions. Rien dans cet affichage n'a été généré par un modèle : chaque caractère est une donnée de l'index — c'est l'UX défendue par la leçon 0006.

Vérifiez que c'est acquis

1. Pourquoi fusionner par le rang (RRF) plutôt que par une somme des scores des deux bras ?

Le premier bras rend des cosinus entre −1 et 1, le second des produits scalaires sparse sans borne : les additionner reviendrait à additionner des grandeurs sans unité commune. Le rang, lui, est la seule grandeur que les deux bras expriment dans la même unité ; RRF s'en sert comme dénominateur commun (veille §6.2).

2. Le cross-encoder ne relit que 20 candidats. Pourquoi pas les 50 de chaque bras, ou le top-5 directement ?

Un bi-encodeur précalcule les vecteurs et compare en millisecondes ; un cross-encoder relit la paire complète à la requête, ce qui est impensable sur 15 M de chunks mais anodin sur 20. Quant au top-5 sans marge : si un attendu sort 9ᵉ de la fusion, le rerank ne peut pas le voir ; 20 lui laisse une chance de le remonter — c'est la logique de l'entonnoir, rappel d'abord, précision ensuite (leçon 0005).

3. Pourquoi le résultat renvoie-t-il son parent depuis un fichier, et non depuis la base vectorielle ?

Encoder la séance entière noierait dans un vecteur unique le sens de 165 interventions ; le pattern parent-document encode l'enfant et restitue le parent (leçon 0002). Le fichier de parents vit sur disque, et l'étape 2 l'y a écrit en verbatim ; la recherche ne fait que le rattacher au résultat.
