Étape 4 en code : indexer dans Qdrant, quantifié et filtrable

À la fin de cette fiche, vous pouvez réécrire vous-même la seconde moitié de atelier/indexation.py : la création de la collection (dense cosinus quantifié int8, sparse, index de payload) et l'envoi des points, dont les identifiants déterministes rendent la réindexation sans effet de bord.

Le principe de l'étape. Qdrant (Apache-2.0) reçoit par point deux vecteurs nommés (dense et sparse) et un payload (le charge de métadonnées qui accompagne chaque point). Deux décisions de la leçon 0004 y sont matérialisées : la quantification scalaire int8, qui divise la mémoire des vecteurs par 4, et les index de payload, qui rendent le pré-filtrage (« Chambre, 1880-1900, orateur X ») efficace plutôt qu'après coup. La troisième décision est propre au batch : des identifiants de points dérivés, et non attribués par le serveur, pour que réindexer deux fois ne duplique rien.

Le service et le client

Qdrant tourne en Docker mono-nœud (make up lance le docker-compose.yml fourni, port 6333, données dans un volume Docker). Le code ne parle au service que par le client officiel qdrant-client (version ≥ 1.20) ; le tableau de bord http://localhost:6333/dashboard permet de tout vérifier à l'œil.

Attention d'inventaire. L'API du client a bougé sur cette série de versions : les types s'écrivent Prefetch, ScalarQuantizationConfig, DatetimeRange, et le nombre de points se lit client.count(collection_name).count. La note d'inventaire de l'atelier (NOTES.md) est formelle : ne « modernisez » pas ces imports sans relancer make test-complet, qui est le seul juge de la compatibilité.

Des identifiants de points dérivés, pas inventés

Qdrant accepte des identifiants de points au format UUID. Si le client en tirait un au hasard à chaque passe, chaque réindexation créerait des doublons. Le module dérive donc l'identifiant de l'identifiant du granulat lui-même, par un UUID de version 5 (un UUID déterministe, dérivé sans retour possible d'un espace de nom et d'une chaîne par fonction de hachage) :

NAMESPACE_POINT = uuid.uuid5(uuid.NAMESPACE_URL, "atelier-axe1-jo-debats")

def point_id(chunk_id: str) -> str:
    """Identifiant de point déterministe (UUID v5) → re-indexation idempotente."""
    return str(uuid.uuid5(NAMESPACE_POINT, chunk_id))

L'espace de nom est lui-même un UUID v5 calculé une fois pour toutes à partir d'une chaîne du projet ; ce double niveau est la convention usuelle pour ne jamais entrer en collision avec l'espace de nom standard uuid.NAMESPACE_URL lui-même. Le gain est entier : un upsert (envoyer en créant ou remplaçant) du granulat …-i007-c01 touchera toujours le même point, la première fois qu'on l'envoie comme la vingtième, et le test d'idempotence (compte identique après deux passes) devient possible.

Créer la collection : deux vecteurs, une quantification, cinq index

La fonction est écrite pour être relancée : elle n'écrase rien par défaut, et elle recrée tout sur demande explicite. Les types viennent tous de qdrant_client.models :

def creer_collection(client, config, effacer: bool = False) -> None:
    from qdrant_client.models import (
        DatetimeIndexParams, DatetimeIndexType, Distance, KeywordIndexParams,
        KeywordIndexType, ScalarQuantization, ScalarQuantizationConfig,
        ScalarType, SparseVectorParams, VectorParams,
    )

    existantes = {c.name for c in client.get_collections().collections}
    if config.collection in existantes and effacer:
        client.delete_collection(collection_name=config.collection)
        existantes.discard(config.collection)
    if config.collection not in existantes:
        client.create_collection(
            collection_name=config.collection,
            vectors_config={
                # cosinus : les embeddings bge-m3 sont comparés en angle
                "dense": VectorParams(size=config.dim, distance=Distance.COSINE),
            },
            sparse_vectors_config={"sparse": SparseVectorParams()},
            # leçon 0004 : la quantification scalaire int8 divise la mémoire par 4
            quantization_config=ScalarQuantization(
                scalar=ScalarQuantizationConfig(type=ScalarType.INT8),
            ),
        )
    for champ in ("chambre", "orateur", "parent_id", "session"):
        client.create_payload_index(
            collection_name=config.collection, field_name=champ,
            field_schema=KeywordIndexParams(type=KeywordIndexType.KEYWORD),
        )
    client.create_payload_index(
        collection_name=config.collection, field_name="date",
        field_schema=DatetimeIndexParams(type=DatetimeIndexType.DATETIME),
    )
  • Deux vecteurs nommés. Une collection Qdrant peut porter plusieurs vecteurs par point ; on les nomme, et chaque bras de recherche dira lequel il interroge (using="dense" plus tard). Le vecteur sparse ne déclare ni dimension (elle est implicite, portée par les indices) ni distance (elle est fixée par le produit scalaire sparse).
  • Distance cosinus. Les vecteurs de bge-m3 sont normalisés à la norme 1 à l'encodage (page 0015) ; cosinus est la distance cohérente avec ce choix, et Qdrant peut alors optimiser en interne.
  • Quantification scalaire int8. Chaque composante fp32 (32 bits à virgule flottante) est rangée dans un entier 8 bits par une transformation affine calibrée : la mémoire de la division par 4 annoncée par la leçon 0004, au prix d'une perte de précision mesurée par vos propres Q&R, jamais par un classement public.
  • Index de payload. Sans index, un filtre est évalué point par point après la recherche vectorielle ; avec un index mot-clé (exact) sur chambre, orateur, parent_id et session, et un index date sur date, Qdrant construit l'ensemble admissible avant de chercher : c'est le pré-filtrage qui rend le « en 1922, uniquement au Sénat » gratuit, celui-là même qui distingue un outil scientifique d'une démonstration (leçon 0009). La recréation d'un index déjà existant est sans effet, d'où la boucle non conditionnelle.

Le payload : tout ce que l'affichage réclamera, en un seul voyage

Le point Qdrant embarque le texte du fragment et toutes ses métadonnées. C'est délibéré : la recherche doit pouvoir afficher un résultat citable (orateur, chambre, date, page du Journal officiel) et remonter son parent sans seconde requête ni jointure applicative.

def _payload(enfant: dict) -> dict:
    return {
        "chunk_id": enfant["id"],
        "intervention_id": enfant["intervention_id"],
        "parent_id": enfant["parent_id"],
        "date": enfant["date"], "chambre": enfant["chambre"],
        "session": enfant["session"], "seance": enfant["seance"],
        "orateur": enfant["orateur"], "orateur_brut": enfant["orateur_brut"],
        "role": enfant.get("role"), "groupe": enfant.get("groupe"),
        "résumé": enfant.get("résumé"),
        "page_jo": enfant["page_jo"],
        "chunk_index": enfant["chunk_index"], "chunk_total": enfant["chunk_total"],
        "texte": enfant["texte"],
    }

Le prix de ce choix est la redondance (le texte vit à la fois dans le payload Qdrant et dans enfants.jsonl) ; le bénéfice est une recherche qui se suffit de sa propre réponse. Sur un index de millions de chunks, on discuterait le champ texte (les payloads sont stockés en clair), mais la version CPU de la veille raisonne en dizaines de gigaoctets, pas en teraoctets.

Envoyer les points : lots de 128 et acquittement

def etape4_indexer(config, client=None) -> int:
    from qdrant_client import QdrantClient
    from qdrant_client.models import PointStruct, SparseVector

    client = client or QdrantClient(url=config.qdrant_url)
    creer_collection(client, config)

    enfants = lire_jsonl(config.enfants_path)
    cache = charger_cache(config.cache_path)
    manquants = [e["id"] for e in enfants if e["id"] not in cache]
    if manquants:
        raise RuntimeError(
            f"{len(manquants)} granulats sans vecteurs en cache — lancer d'abord « encoder »"
        )

    points = [
        PointStruct(
            id=point_id(enfant["id"]),
            vector={
                "dense": cache[enfant["id"]]["dense"],
                "sparse": SparseVector(**_sparse_brut(cache[enfant["id"]]["sparse"])),
            },
            payload=_payload(enfant),
        )
        for enfant in enfants
    ]
    taille_lot = 128
    for debut in range(0, len(points), taille_lot):
        client.upsert(
            collection_name=config.collection,
            points=points[debut:debut + taille_lot],
            wait=True,
        )
    return len(points)

Quatre lectures utiles. La vérification des vecteurs manquants transforme un enchaînement raté (« j'ai lancé indexer avant encoder ») en une phrase commandable. SparseVector(indices=[…], values=[…]) est le format d'un vecteur sparse sur le fil : deux tableaux parallèles, les identifiants de jetons et leurs poids — _sparse_brut convertit la carte texte → nombres du cache en ces deux tableaux. L'envoi par lots de 128 bornes la taille de chaque requête HTTP, et wait=True fait attendre au serveur l'acquittement de l'écriture : sans lui, le test qui suit immédiatement l'upsert pourrait compter un index pas encore appliqué — le genre de condition de course qui fait écrire « mon indexation est aléatoire » dans un billet d'humeur. Enfin le paramètre client=None est la même couture que pour l'encodeur : un test d'intégration injecte son propre client, la ligne de commande construit celui de la configuration.

Comment le module est testé

L'étape 4 est la première à exiger un service : ses tests portent la marque integration et tournent avec Qdrant démarré (make test-complet), dans une collection de test distincte :

  • test_collection_creee_avec_quantification_et_sparse relit la configuration de collection côté serveur et vérifie la quantification int8 et le vecteur sparse (accès config.params.sparse_vectors).
  • test_payload_et_indices_de_filtre vérifie la présence des index de payload déclarés.
  • test_upsert_idempotent envoie deux fois les mêmes points et compte un — la propriété « réindexer ne duplique rien », mesurée, pas supposée.
  • test_point_id_deterministe vérifie que le même chunk_id donne le même UUID.

À vérifier de votre côté : après uv run python -m atelier indexer, le tableau de bord http://localhost:6333/dashboard montre la collection jo_debats avec 165 points ; relancez la commande et le compte reste 165.

Vérifiez que c'est acquis

1. Que se passerait-il si point_id() tirait un UUID au hasard à chaque exécution ?

Un upsert ne remplace que le point de même identifiant : avec des UUID aléatoires, chaque passe ajoute des copies des mêmes granulats, et la recherche rendrait deux fois le même fragment. L'UUID v5 dérivé du chunk_id fixe l'identité du point en amont, et la relance devient sans effet — le test test_upsert_idempotent est là pour ce risque.

2. À quoi sert l'index de payload sur le champ chambre ?

Sans index, Qdrant évalue le filtre sur chaque point candidat après les avoir rapprochés, et le rappel s'écroule quand le filtre est sélectif. Avec l'index mot-clé, l'ensemble des points admissibles est construit avant la descente dans le graphe HNSW : c'est le pré-filtrage qui rend les facettes de la leçon 0009 gratuites à chaque clic.

3. Pourquoi wait=True sur l'upsert, alors qu'il ralentit l'écriture ?

wait=True demande au serveur d'acquitter après application du point d'écriture ; sans lui, une vérification lancée juste après l'upsert peut voir un index pas encore à jour et conclure à une perte de données. Sur un gros batch, on peut relâcher cette attente et interroger le statut des tâches d'indexation asynchrones — dans l'atelier, la simplicité fiable prime.
